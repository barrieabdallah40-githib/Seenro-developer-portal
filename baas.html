1. Platform overview

SEENRO Backend as a Service (BaaS) is intended to give independent developers, startups and businesses a common backend platform for building and operating applications.

Instead of building every backend component from scratch, a developer should be able to create a SEENRO project and integrate services through documented APIs and, as they become available, supported SDKs.

The platform vision
  • Customer identity and authentication for applications.
  • Project-scoped data and database services.
  • File, image and video storage.
  • APIs, developer credentials and integration tools.
  • Reusable notifications and event-driven services.
  • Project-level quotas, request limits and resource safeguards.
  • Future automation, AI and defensive security services.

SEENRO is an independent platform. Its services, infrastructure, credentials and developer experience are managed as SEENRO products.

2. Core concepts

Developer account

A developer account is used to sign in to the SEENRO Developer Portal and manage projects. It is separate from the customer accounts that developers create for users of their own applications.

Project

A project represents an application or backend environment managed by a developer. Project-scoped credentials and resources must not grant access to another project.

Customer

A customer is an end user of an application built by a SEENRO developer. Customer identity and access must remain scoped to the relevant project.

Public project identifier

The public customer-authentication routes use a public project identifier with the proj_pub_ prefix. It identifies the project for public client requests; it is not a secret developer credential.

Project API key and Storage API key

These are separate server-side credentials for different API permission systems. A project API key must not be treated as a Storage API key, or vice versa.

3. Developer workflow

  1. Create or sign in to a developer account.
  2. Create a project for the application.
  3. Choose the services the application needs.
  4. Configure project credentials and permissions.
  5. Keep secret credentials on a trusted backend, never in browser or mobile application source code.
  6. Integrate the documented API endpoints.
  7. Test authentication, access boundaries, error handling and usage limits.
  8. Review deployment status and production readiness before launching.

The exact project-management interface and availability of individual services depend on the deployed portal and Core release.

Project API key scopes

The inspected project API key scope model includes project, data and authentication read/write scopes. The trusted customer-auth routes are protected by the auth:read and auth:write scope enforcement.

Storage permissions

  • can_read — permits Storage read operations.
  • can_write — permits Storage write and administrative operations.
  • can_issue_uploads — permits issuing temporary upload authorizations.

Grant only the permissions required by each server component. Store secrets in a server-side secret manager or protected environment configuration, and rotate credentials if exposure is suspected.

6. Customer Authentication

SEENRO Customer Authentication is intended for the end users of applications built by developers. It is not the same as developer sign-in to the SEENRO portal.

Customer identity rules

  • Phone number and password are the required customer registration and login credentials.
  • Email is optional; it is not the customer login identifier.
  • Customer authentication is scoped to a developer project.
  • Customer access tokens are used for protected customer operations.

Public customer-authentication routes

These routes are designed for browser and mobile clients and resolve the project using its public project identifier.

POST /public/projects/{public_project_id}/auth/register
POST /public/projects/{public_project_id}/auth/login
GET  /public/projects/{public_project_id}/auth/me
POST /public/projects/{public_project_id}/auth/logout

Trusted backend routes

Trusted routes use a project-bound developer API key and the required authentication scope.

POST /projects/{project_id}/auth/register
POST /projects/{project_id}/auth/login
GET  /projects/{project_id}/auth/me
POST /projects/{project_id}/auth/logout

Customer sessions in the inspected implementation have a seven-day lifetime. Tokens are stored as hashes server-side and are scoped to the project and customer.

Never expose a secret project API key in a browser or mobile application. Public customer routes use the public project identifier. Trusted routes belong on a developer-controlled backend.

See the Customer Authentication Integration Guide for request examples, responses and integration details.

7. Database and data services

A complete SEENRO BaaS database service is intended to provide developers with project-scoped data storage, controlled access and APIs for application data.

Target database architecture

  • PostgreSQL as the foundation for project database services.
  • Strong separation between platform control-plane data and project application data.
  • Project-scoped database access and authorization.
  • Row-Level Security (RLS) enabled and forced on every applicable project table.
  • Database roles that cannot bypass the intended isolation controls.
  • Transaction-local project and user context rather than trusting client-supplied ownership claims.
  • Backups, restoration procedures and a future point-in-time recovery capability.
Implementation status: The PostgreSQL per-project database and RLS architecture described above is a target, not a claim that it is already deployed. The Core implementation inspected during preparation used SQLite. Do not assume that the existing database or legacy Data API provides the complete planned PostgreSQL BaaS experience.

Requirements before database BaaS is production-ready

  • Provisioning and lifecycle management for project databases.
  • Verified isolation tests across projects, users and roles.
  • Safe schema migrations and version management.
  • Connection limits, query limits and resource quotas.
  • Backup, restore and disaster-recovery tests.
  • Documented database API, client access model and error behavior.

8. Storage and Media

SEENRO Storage provides project-scoped file operations and customer media workflows. The inspected implementation includes Storage API keys, temporary upload authorization, customer linking and protected media retrieval.

Customer-to-Storage identity

A developer can associate an external customer identifier with a customer-authentication user in the same project. This mapping allows Storage to associate objects with the correct application customer.

Upload workflow

  1. The developer's backend requests a temporary upload authorization using a Storage key with the required permission.
  2. SEENRO issues a short-lived, one-use upload token.
  3. The client uploads the raw file using the temporary token.
  4. SEENRO validates the content and enforces applicable limits.
  5. The upload response returns file metadata, including the object identifier and content details.

Inspected media limits

  • Supported images: up to 25 MiB.
  • PDF files: up to 50 MiB.
  • MP4, MOV and WebM videos: up to 250 MiB and five minutes.
  • Video size and duration limits are independent.

Private media retrieval uses customer authentication and checks ownership or an active permitted share. It is not intended to expose permanent public URLs for private customer objects.

See the Storage Integration Guide for exact endpoints, permissions, upload requests and media access details.

9. Notifications and events

SEENRO's notification direction is a shared, extensible delivery system for events across Core services—not a worker hard-coded for one feature.

The intended design uses a persistent notification/outbox pipeline with reusable delivery, retry, deduplication, templates and event/task registration. New notification types should be able to plug into the shared worker without redesigning the worker engine.

Potential event sources include customer authentication, account recovery, Storage events, project activity and future platform services. Actual event types and delivery channels must be documented only after their handlers and deployment are verified.

Do not assume that every event, channel, retry policy or notification template described as a future capability is already enabled in production.

10. Security and project isolation

Project isolation is a foundational requirement of SEENRO BaaS. A developer must not be able to access another project's customers, records, files, keys or usage data.

Security principles

  • Enforce project ownership on the server for every protected operation.
  • Bind secret API keys to a specific project and enforce their permissions.
  • Keep public identifiers separate from secret credentials.
  • Authenticate customer requests and verify ownership before returning private data.
  • Validate uploaded content; do not trust filenames or client-provided content types.
  • Apply rate limits and request-size limits to sensitive endpoints.
  • Store password hashes and session-token hashes rather than plaintext credentials.
  • Protect environment files, signing secrets, database files and backups.
  • Log security-relevant events without logging passwords, tokens or secret keys.

PostgreSQL isolation target

For the planned PostgreSQL service, every project table must have RLS enabled and forced, with policies based on trusted transaction context. Application roles must not have privileges that bypass those policies. Isolation must be tested directly, including attempts to access another project by changing identifiers.

Security review before launch

  • Cross-project authorization tests.
  • Credential scope and revocation tests.
  • Session expiry and logout tests.
  • Rate-limit and abuse tests.
  • Upload validation and one-time-token tests.
  • Backup access and secret exposure review.

11. Target platform architecture

The long-term architecture separates platform administration from each developer's application data and services.

Developer Portal
Developer accounts, projects, configuration and credentials.

SEENRO Core API
Project authorization, customer authentication, Storage, data services, notifications and service orchestration.

Control plane
Developer identities, project registry, service configuration and resource provisioning.

Project data plane
Isolated project databases, customer data and project-owned resources.

Object storage
Private customer files and media, with project ownership and controlled access.

Background workers
Persistent jobs, notifications, retries and future automation tasks.

This is the target separation of responsibilities. It should not be interpreted as a complete inventory of currently deployed infrastructure.

12. Production readiness checklist

Before an application relies on SEENRO in production, developers should verify the services and operational guarantees they actually need.

  • Confirm the API base URL and the service release currently deployed.
  • Use separate projects for environments where isolation is required.
  • Keep secret keys on trusted servers and restrict their permissions.
  • Test customer registration, login, logout and session expiry.
  • Test Storage uploads, file validation and private media authorization.
  • Test that one project cannot read another project's data or files.
  • Implement safe retries and handle rate limits and server errors.
  • Monitor application errors, API limits and resource consumption.
  • Confirm backup and restoration arrangements for the services being used.
  • Review service availability and known limitations before launch.

13. Availability and roadmap

SEENRO is being developed in stages. The labels below prevent planned capabilities from being mistaken for production guarantees.

Implemented routes inspected
Customer authentication and Storage capabilities described in the linked integration guides.

Verify deployment
Portal project-management features, API release versions and notification worker behavior must be checked against the current deployed release.

Planned architecture
Full PostgreSQL project database provisioning, comprehensive RLS-based data isolation, broader SDK coverage, expanded AI and automation services, and additional operational capabilities.

Availability can change as releases are deployed. The authoritative integration contract is the API behavior of the specific release a developer is using, together with the current service documentation.
