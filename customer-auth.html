Customer Authentication

Build customer registration, login and session-based authentication into applications and websites using SEENRO Core.

What it provides

  • Customer registration using a phone number and password.
  • Customer login using a phone number and password.
  • Optional email address during registration.
  • Project-scoped customer identities and sessions.
  • Authenticated customer profile retrieval and logout.
  • Allowed-origin configuration for browser applications.

Important: Customer Authentication is separate from your SEENRO developer account authentication and separate from SEENRO Storage.

API configuration

API base URL

https://api.seenrotech.com/api/v1

Use your project's public ID, which begins with proj_pub_. Customer-facing applications must not contain secret developer API keys.

Register a customer

const response = await fetch(
  "https://api.seenrotech.com/api/v1/public/projects/PROJECT_PUBLIC_ID/auth/register",
  {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      phone_number: "+232XXXXXXXX",
      password: "A-strong-customer-password",
      email: "customer@example.com"
    })
  }
);

const result = await response.json();

Email is optional. Do not make email mandatory in your registration form. Use the exact request fields and response format documented by the deployed API.

Log in a customer

const response = await fetch(
  "https://api.seenrotech.com/api/v1/public/projects/PROJECT_PUBLIC_ID/auth/login",
  {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      phone_number: "+232XXXXXXXX",
      password: "A-strong-customer-password"
    })
  }
);

const result = await response.json();

Customer login uses phone number and password. Email is not a login credential.

Get the current customer

const response = await fetch(
  "https://api.seenrotech.com/api/v1/public/projects/PROJECT_PUBLIC_ID/auth/me",
  {
    headers: {
      "Authorization": `Bearer ${customerSessionToken}`
    }
  }
);

const customer = await response.json();

Log out

const response = await fetch(
  "https://api.seenrotech.com/api/v1/public/projects/PROJECT_PUBLIC_ID/auth/logout",
  {
    method: "POST",
    headers: {
      "Authorization": `Bearer ${customerSessionToken}`
    }
  }
);

API routes

MethodRoutePurpose
POST/public/projects/{public_project_id}/auth/registerRegister customer
POST/public/projects/{public_project_id}/auth/loginLog in customer
GET/public/projects/{public_project_id}/auth/meGet authenticated customer
POST/public/projects/{public_project_id}/auth/logoutEnd customer session

Phone verification status

Customer phone verification is not yet available in this release. New customer accounts are not proof of phone ownership; the phone verification field defaults to unverified. SMS/OTP delivery and phone-based recovery are not included in this v1 release.

Do not display a verified-phone status or rely on phone ownership as a security guarantee until a verification flow is implemented.

Customer Auth usage and credits

  • Each project receives 100 free Customer Auth units once.
  • After the free allocation, the proposed unit price is SLE 0.25 per unit.
  • One unit represents one unique customer active in one project on one UTC calendar day.
  • Multiple logins or sessions by the same customer in the same project on the same UTC day count as one unit.
  • The same customer active on another UTC day can consume another unit.

Metering status: The release includes the Customer Auth credit and purchase foundation. DAU metering and usage enforcement are not yet enabled. Do not treat the DAU calculation as currently enforced billing.

Customer Auth credits are separate from Storage credits and Storage subscriptions. Billing is intended to use SEENRO's existing billing and Monime integration, not a separate billing system.

Security requirements

  • Keep customer data and sessions within the correct project.
  • Use the project's public ID in browser and mobile applications.
  • Never expose sk_live_ developer secret keys in client-side code.
  • Never expose st_live_ Storage keys in client-side code.
  • Use HTTPS and protect customer session tokens.
  • Configure allowed origins for browser applications. CORS is not an authentication or authorization boundary.
  • Do not confuse developer account credentials with customer account credentials.
