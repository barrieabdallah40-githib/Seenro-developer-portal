SEENRO CORE · CUSTOMER AUTHENTICATION

Authenticate your customers.

Integrate customer registration, login, session verification, and logout into websites and mobile applications using SEENRO Application Auth.

Customer authentication is separate from developer-portal authentication. Your customers use your application's customer accounts; they do not need SEENRO developer accounts.

01 · BEFORE YOU START

Project details and credentials

Create a project in the SEENRO Developer Portal. Obtain the following values from the project workspace.

ValuePurposeWhere it belongs
https://api.seenrotech.com/api/v1SEENRO Core API base URL.Application configuration.
proj_pub_...Public project identifier used by public customer-auth routes.May be included in browser and mobile application configuration.
Numerical project IDProject identifier used by trusted, project-scoped server routes, including Storage.Backend configuration.
Project API keyAuthorizes permitted trusted server-to-server project operations.Backend secret storage only.

Do not confuse the two project identifiers. The public identifier begins with proj_pub_ and is not the numerical project ID. The public identifier is designed for public customer-auth routes. The numerical ID is used by trusted project routes such as the Storage customer-link and upload-authorization endpoints.

Project API keys and Storage API keys are different credentials. A project API key does not automatically grant Storage permissions.

02 · PUBLIC CLIENT INTEGRATION

Browser and mobile applications

Use the public customer-auth routes when registration and login are called directly from a browser or mobile application. These routes resolve the project using its public project identifier and do not require a developer project API key.

Customer registration

Registration requires a phone number and password. Email is optional. Email is not the customer login identifier.

POST https://api.seenrotech.com/api/v1/public/projects/proj_pub_YOUR_PUBLIC_ID/auth/register
Content-Type: application/json

{
  "phone_number": "+232XXXXXXXX",
  "email": "customer@example.com",
  "password": "a-strong-customer-password"
}

A successful registration returns HTTP 201 and a customer object, an access token, its token type, and the session expiry duration. The response has this shape:

{
  "user": {
    "id": 123,
    "phone_number": "+232XXXXXXXX",
    "email": "customer@example.com",
    "phone_verified": false
  },
  "access_token": "CUSTOMER_SESSION_TOKEN",
  "token_type": "Bearer",
  "expires_in": 604800
}

The example user ID and token are illustrative. Use the values returned by your actual API response.

Customer login

Customers sign in with their phone number and password.

POST https://api.seenrotech.com/api/v1/public/projects/proj_pub_YOUR_PUBLIC_ID/auth/login
Content-Type: application/json

{
  "phone_number": "+232XXXXXXXX",
  "password": "the-customer-password"
}

A successful login returns HTTP 200, the customer user information, and a new session access token.

Important registration rules

  • Phone number and password are the required customer credentials.
  • Email is optional and is not used as the login identifier.
  • Passwords must be between 8 and 128 characters.
  • Keep the returned access token associated with the signed-in customer.

03 · TRUSTED SERVER INTEGRATION

Calls made by your backend

SEENRO also exposes project-scoped customer-auth routes for trusted server-to-server integrations. These routes use the numerical project ID and a project-bound API key with the appropriate auth:read or auth:write scope.

POST https://api.seenrotech.com/api/v1/projects/NUMERICAL_PROJECT_ID/auth/register
Authorization: Bearer YOUR_PROJECT_API_KEY
Content-Type: application/json

{
  "phone_number": "+232XXXXXXXX",
  "email": "customer@example.com",
  "password": "a-strong-customer-password"
}

For backend login, use:

POST https://api.seenrotech.com/api/v1/projects/NUMERICAL_PROJECT_ID/auth/login
Authorization: Bearer YOUR_PROJECT_API_KEY
Content-Type: application/json

{
  "phone_number": "+232XXXXXXXX",
  "password": "the-customer-password"
}

These project-scoped routes require a project API key bound to the same project in the URL. Do not use a key belonging to another project.

Never send a project API key to the browser or mobile application. If a client needs to register or log in directly, use the public /public/projects/{public_project_id}/auth/... routes instead.

04 · CUSTOMER SESSION

Verify and end a customer session

Use the customer access token returned by registration or login as a Bearer token for the session routes.

Get the current customer

GET https://api.seenrotech.com/api/v1/public/projects/proj_pub_YOUR_PUBLIC_ID/auth/me
Authorization: Bearer CUSTOMER_ACCESS_TOKEN

The response includes the authenticated customer's user ID, phone number, email where present, and phone-verification status.

Log out

POST https://api.seenrotech.com/api/v1/public/projects/proj_pub_YOUR_PUBLIC_ID/auth/logout
Authorization: Bearer CUSTOMER_ACCESS_TOKEN

A successful logout returns:

{
  "message": "logged out"
}

Equivalent project-scoped routes are available under /projects/{project_id}/auth/... when called with a valid project API key and the customer session token as required by the endpoint.

Customer sessions are project-scoped, expire, and are stored server-side as token hashes. Do not assume a token is permanent.

05 · SECURITY PRACTICES

Protect credentials and customer sessions

  • Use HTTPS for all production API requests.
  • Keep project API keys in backend environment variables or a secret manager. Never commit them to source control.
  • The public project identifier is not a substitute for a secret key, and a secret key must never be exposed as a public identifier.
  • Do not log customer passwords, access tokens, or secret API keys.
  • Protect customer session tokens against theft. Use secure, platform-appropriate session storage and avoid exposing tokens to untrusted scripts.
  • Validate and authorize sensitive business actions in your own backend. A customer being authenticated does not automatically authorize every action in your application.
  • Do not accept a customer ID or application-user ID from an untrusted client as proof of identity when performing trusted Storage identity linking.

The public customer-auth endpoints are intended to avoid exposing a developer secret to the client. Your own application still needs sound session handling, authorization, input validation, and abuse protection.

06 · TROUBLESHOOTING

Understand common failures

HTTP statusWhat it usually meansWhat to check
400Invalid request data.Check required fields, phone number, and password length.
401Missing or invalid authentication.Check the Bearer token and whether the customer session is still valid.
403Insufficient project-key permissions or access denied.Check the key's scopes and project association.
404Project or requested resource not found.Check the project identifier and route.
409Conflicting account or resource state.Check whether the phone number or requested identity is already in use.

SEENRO Core is in early access. Test registration, login, token expiry, logout, error handling, and your application's authorization logic before production rollout.
