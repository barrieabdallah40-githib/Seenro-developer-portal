02 · GET STARTED

Quick start

  1. Create an account. Register in the developer portal; complete email verification if enabled.
  2. Create a project. Sign in and create a project in your workspace.
  3. Create a project API key. Select only the scopes your trusted server needs.
  4. Store the secret safely. The full key is shown only at creation. Save it in a server-side secret manager.
  5. Call the API. Use the API base URL and endpoint-specific authentication method.

Never put a secret project API key in browser JavaScript, a public repository, or a mobile application bundle.

03 · ACCESS CONTROL

Authentication and API keys

Developer session

The portal uses a developer login session to manage that developer's projects and API keys. These management calls use the session as a Bearer token.

Project-bound developer API keys

Keys are project-bound. Core stores a hash; the full secret is returned only at creation. They are intended for trusted server-to-server use. Core checks project association and assigned permissions.

ScopePurpose
projects:readRead permitted project information.
projects:writeCreate or modify permitted project resources.
data:readRead project data records.
data:writeCreate, update, or delete project data records.
auth:readPermitted application-authentication reads.
auth:writePermitted application-authentication writes.

These are the scopes currently exposed by the portal. Do not assume they grant storage permissions. Storage-key authentication is separate; use the matching Core contract for its credential format and schema.

05 · DEVELOPER STORAGE

Store and serve customer media

SEENRO Storage provides project-scoped object storage, customer uploads, media viewing and sharing, Storage API key management, usage tracking, and subscription checkout. Developers integrate Storage into their own applications and websites. Their customers do not need SEENRO developer accounts or Storage API credentials.

Keep Storage secrets on your backend. A secret st_live_ key must never appear in browser JavaScript, a mobile application, a public repository, or code delivered to customers. Your trusted server uses it for authorized Storage operations. Customers upload using a short-lived, single-use upload token instead.

Storage key permissions

  • Read (can_read): permits Storage-key read operations.
  • Write (can_write): permits Storage-key write and administration operations, including customer linking, group management, group membership management, and public-page configuration.
  • Issue uploads (can_issue_uploads): permits the backend to issue temporary customer upload authorizations.

For the customer upload and private-viewing integration, the backend needs can_write to link customers and can_issue_uploads to issue upload tokens. A key can have multiple capabilities. Use least privilege.

Customer upload and private viewing

Use the same stable external customer ID for linking and upload authorization. The identity link associates a Storage customer with a SEENRO application user in the same project. Uploading alone does not create this application-user association.

  1. Authenticate your customer. Your backend first authenticates the customer with SEENRO Application Auth. Register with POST /api/v1/projects/{project_id}/auth/register or log in with POST /api/v1/projects/{project_id}/auth/login, using a project-bound API key with auth:write. Both endpoints return user.id and access_token. Use user.id as application_user_id when linking the customer, and keep access_token as the customer's Bearer session credential. Never expose the project API key or Storage developer secret to the customer-facing app.
  2. Link the customer from your trusted backend. Call the customer-link endpoint with a Storage key having can_write. Supply the stable external customer ID and corresponding project-scoped SEENRO application_user_id.
  3. Issue an upload authorization. Your backend calls the upload-authorization endpoint using a key with can_issue_uploads and the exact same external customer ID.
  4. Upload from the customer's app. The app sends the file using the temporary token as its Bearer credential. It never receives the developer's st_live_ key.
  5. View private media. The app requests the private media endpoint using the customer's valid SEENRO application-user session. Core checks ownership or an applicable active share.

Link the customer before relying on private viewing. The external customer ID must match exactly between linking and upload authorization, and the linked application user must be the user whose valid session is used to view the media. Upload can succeed without this link, but private ownership access will not automatically infer the relationship.

Customer sharing and access boundaries

  • Media is private by default. Private viewing uses the authenticated application-user session and Core's ownership/share checks.
  • Customer-to-customer share creation and revocation are authenticated customer operations, not developer Storage-key permissions.
  • Developers manage customer links, groups, group members, and public-page configuration through trusted backend calls authorized by can_write.
  • Group and customer shares are checked for membership or recipient, revocation, and expiry.
  • Unlisted and public-page access are distinct sharing modes. A public-facing page does not mean every object is permanently public or that private storage buckets are exposed.
  • Sharing is scoped and revocable. Do not treat a share token as a permanent public object URL.

Upload limits and file handling

Current documented product limits are non-video files up to 100 MiB and MP4, MOV, and WebM videos up to 250 MB and 5 minutes. Video size and duration limits are independent. Original uploaded bytes are preserved without forced compression.

Payment and capacity safety

  • Checkout starts a payment flow; it does not itself grant capacity.
  • Capacity is granted only after Core independently verifies settlement.
  • A browser redirect or client-supplied payment status is not proof of payment.

These routes and authorization boundaries reflect the inspected Core implementation. Developers should still test their complete application integration, including identity mapping, upload expiry/failure handling, private viewing, sharing expiry/revocation, capacity, payment settlement, and renewal.
