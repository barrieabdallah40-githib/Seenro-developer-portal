SEENRO CORE · STORAGE AND CUSTOMER MEDIA

Store and serve customer media.

A complete integration path for linking your application customers to Storage, issuing secure upload authorizations, uploading files, and serving private media.

API base URL https://api.seenrotech.com/api/v1

Your trusted backend holds the Storage API key. Your customer-facing application receives only a short-lived, single-use upload token when it needs to upload a file.

There are two project identifiers. Public customer authentication uses the public identifier beginning proj_pub_. Trusted Storage routes use the numerical project ID. Do not put the public identifier into a route that expects the numerical ID.

There are also two different developer key types. Project API keys authorize project API operations using their project scopes. Storage API keys authorize Storage operations using Storage-specific capabilities. They are not interchangeable.

02 · STORAGE API KEY

Create a key with the required permissions

In the SEENRO Developer Portal, open your project and its Storage API key management page. Create a Storage API key and enable the permissions needed by your integration.

PermissionWhat it authorizes
can_readStorage-key read operations.
can_writeStorage write and administration operations, including customer linking, group management, group membership, and public-page configuration.
can_issue_uploadsIssuing temporary customer upload authorizations.

For the complete customer-media workflow described in this guide, create a key with can_read, can_write, and can_issue_uploads. The permissions are independent; enable only what the backend needs.

Storage keys use the st_live_ prefix. The full secret is shown only when the key is created. Save it immediately in your backend's environment configuration or secret manager.

Never put an st_live_ key in frontend JavaScript, a mobile application bundle, a public repository, or a request sent directly by a customer device.

03 · CUSTOMER IDENTITY LINKING

Connect Storage customers to Application Auth

Storage customer identity and SEENRO Application Auth identity are related but distinct records. The link allows Core to recognize which authenticated application user owns a customer's private media.

  1. Authenticate the customer. Register or log in using SEENRO Application Auth. For browser and mobile clients, use the public customer-auth routes. See the Customer Authentication Integration Guide.
  2. Read the trusted identity. Obtain the customer's user.id and session token from the successful authentication response. The user ID must come from the authenticated SEENRO response, not from an untrusted client-supplied claim.
  3. Choose a stable external customer ID. Your backend should use a stable identifier from your own customer system, such as your own immutable customer record ID. Do not use a value supplied by an unauthenticated client as proof of identity.
  4. Link from your backend. Call the customer-link route using the Storage API key with can_write.

Customer-link request

POST https://api.seenrotech.com/api/v1/projects/NUMERICAL_PROJECT_ID/storage/customers/link
Authorization: Bearer YOUR_STORAGE_API_KEY
Content-Type: application/json

{
  "external_customer_id": "your-system-customer-123",
  "application_user_id": 123
}

The field names are important:

  • external_customer_id is your stable external customer identifier.
  • application_user_id is the numeric user.id returned by SEENRO Application Auth.

A successful request returns HTTP 200 with a response in this form:

{
  "customer_linked": true,
  "storage_customer_id": 456
}

The returned Storage customer ID is a Storage-side identifier. Keep your external customer ID mapping in your trusted backend if your application needs to look it up later.

A customer identity cannot be reassigned to a different application user. If the same external customer identity is already linked to another application user, Core returns HTTP 409. Resolve the identity conflict in your own account system; do not work around it by trusting a client-provided user ID.

04 · CUSTOMER UPLOAD

Issue a one-time upload authorization

After authenticating the customer, your trusted backend requests an upload authorization. The upload-authorization request uses the same stable external customer identity used in your customer-link operation.

Step 1: Request an upload token

POST https://api.seenrotech.com/api/v1/projects/NUMERICAL_PROJECT_ID/storage/uploads
Authorization: Bearer YOUR_STORAGE_API_KEY
Content-Type: application/json

{
  "customer_id": "your-system-customer-123",
  "max_bytes": 10485760,
  "expires_in": 900
}

The request fields are:

  • customer_id: the same stable external customer ID used in the customer-link operation.
  • max_bytes: optional positive maximum file size in bytes. Values above the server maximum are capped at that maximum.
  • expires_in: optional token lifetime in seconds. The supported range is 60 to 3600 seconds; the default is 900 seconds.

The endpoint requires a Storage key with can_issue_uploads. It returns a short-lived stu_live_ authorization token, an upload ID, expiry information, the byte limit, and a customer reference.

Treat the returned token as a temporary capability. It authorizes exactly one upload and is not a replacement for your Storage API key.

Step 2: Upload the file from the client

Return the temporary upload token to the authenticated customer application. The client sends the file bytes directly to the upload endpoint:

PUT https://api.seenrotech.com/api/v1/storage/uploads
Authorization: Bearer TEMPORARY_UPLOAD_TOKEN
X-Filename: profile-photo.jpg
Content-Type: image/jpeg

[raw file bytes]

Send the raw file body, not a JSON wrapper or a base64 string. Include X-Filename. Send the actual content type when known; otherwise the endpoint supports a default of application/octet-stream.

Do not send the Storage API key with this request. The temporary upload token is the upload credential.

Step 3: Handle the upload result

Only treat the upload as complete after the upload endpoint reports success. Core streams the bytes, enforces the authorization's byte limit, validates the file content, checks media-specific limits, and checks available Storage capacity before recording the object. An expired, reused, failed, oversized, invalid, or capacity-blocked upload must not be treated as a successful upload.

Do not assume that receiving an upload token means the file has been stored. Your application should handle failed uploads and request a new authorization when appropriate.

05 · PRIVATE MEDIA VIEWING

Serve private media to its owner

Private media is retrieved using the customer's SEENRO Application Auth session—not the developer's Storage API key and not the one-time upload token.

GET https://api.seenrotech.com/api/v1/projects/NUMERICAL_PROJECT_ID/storage/media/OBJECT_ID
Authorization: Bearer CUSTOMER_ACCESS_TOKEN

Core checks that the authenticated application user is allowed to view the object. Access is permitted when the user is the linked owner or has an applicable active customer or group share. Revoked and expired shares do not grant access.

The response streams the media content. It is not a JSON object containing a permanent public URL. Your application should handle the HTTP response as media content and respect unsuccessful responses such as unauthorized or not-found results.

The customer must be linked to the Storage identity before relying on private owner access. The link, upload authorization, and private media request must all refer to the same project and intended customer identity.

06 · SHARING AND ACCESS

Extend access without making everything public

SEENRO Storage supports additional sharing mechanisms. These have different authorization rules and should not be treated as interchangeable.

POST /projects/{project_id}/storage/groupsCreate or update a project sharing group. Trusted Storage key with can_write.
POST /projects/{project_id}/storage/groups/{group_key}/membersAdd or remove an application user from a group. Trusted Storage key with can_write.
POST /projects/{project_id}/storage/pagesConfigure a public-facing sharing page. Trusted Storage key with can_write.
POST /projects/{project_id}/storage/sharesCreate a customer-owned share using an authenticated application-user session and ownership checks.
POST /projects/{project_id}/storage/shares/revokeRevoke a customer-owned share using an authenticated application-user session.
GET /storage/shared/{token}View an active unlisted share using its share token.
GET /storage/public/{project_id}/{page_key}/{object_id}View media made available through an enabled public page and valid public-page share.
  • Private media is private by default.
  • Customer share creation and revocation use the authenticated customer session and ownership checks; they are not authorized merely by giving the customer a developer Storage key.
  • Group access depends on membership and an active share.
  • Unlisted shares and enabled public-page shares are distinct access modes.
  • Shares can expire or be revoked. Do not treat a share token as a permanent public object URL.

07 · SECURITY AND OPERATIONS

Keep the integration safe

  • Keep the Storage API key and numerical project configuration on your trusted backend.
  • Never trust a client-submitted application_user_id when linking a customer. Resolve it from the authenticated SEENRO customer identity on the backend.
  • Keep external customer IDs stable and scoped to your own customer records.
  • Do not reuse or store upload tokens as permanent credentials.
  • Use HTTPS, validate customer permissions in your own application, and avoid logging secrets or session tokens.
  • Handle expiry, interrupted uploads, file validation failures, and capacity exhaustion explicitly.
  • Use the least-privilege Storage key permissions your integration needs.

Current file limits

For customer-media uploads, supported images are limited to 25 MiB, PDFs to 50 MiB, and MP4, MOV, and WebM videos to 250 MiB and five minutes. The separate developer Storage object-upload API has a 100 MiB request limit. Limits depend on the upload route and media type. Video size and duration limits are independent. Core validates uploaded content; do not rely only on the filename or client-supplied content type.

Capacity handling

An issued upload token does not reserve unlimited Storage capacity. Core checks available capacity when processing the upload. A capacity-exhausted upload fails; your application should report the failure and direct the project owner to review Storage usage and capacity.
